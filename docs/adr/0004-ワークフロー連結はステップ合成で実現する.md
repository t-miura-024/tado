# ADR-0004: ワークフロー連結はステップ合成（step import）で実現する

## Status

accepted

## Context

Issue #11 でワークフロー内から別ワークフローを呼び出せるようにしたい。
現状は orchestrate ステップのプロンプトで「別ワークフローの init を指示する」プロンプトレベルの連結のみで（`orchestrate` アクションは `src/types/workflow-def.ts` の action 型に定義）、エンジンとしての連結機構（親子セッション）は存在しない。

## Decision

ワークフロー連結は step import（定義時合成）で実現する。WorkflowDef はプレーンな TypeScript であり、`steps: [...partsWorkflow.steps, ...mySteps]` のように別ワークフローのステップ配列を展開して再利用する。エンジン・CLI・schema は変更しない。ランタイム連結（親子セッション・同期呼び出し・`parent_session_id`・`inputs`/`outputs` 宣言・ネスト・循環防止・失敗伝播）は実装しない。

ステップ key の衝突は命名規約で回避する（部品ワークフローのステップは `parts_*`、合成ワークフロー独自のステップは `composed_*` のプレフィックスを付与する。規約の例は `examples/workflow-composition.ts` / `examples/workflow-parts.ts` を参照）。key 衝突を機械的に解消する合成ユーティリティ（`withPrefix` 等）は追加しない。

## Considered Options

- プロンプト駆動のランタイム連結: 親ステップのプロンプトが子の init→next→report ループを LLM に指示する。子完了後の親再開が LLM の指示順守に依存し、決定論の原則と衝突するため不採用。
- エンジン透過駆動: next が親ステップか子ステップかを判別してプロンプトを返す。文脈切り替え・冪等再開・孤児セッション・フックスコープの複雑化と実装量増大のため不採用。
- 合成ユーティリティ（`withPrefix` 等）: step key 衝突を解消するヘルパー。現時点で衝突ケースの実需要がなく、過剰実装のため不採用。

## Consequences

- 単一セッションで全ステップが直列実行されるため、親子再開・孤児セッション・成果物受け渡し・失敗伝播の機構が不要になる。
- 子ブロックを単体のセッションとして status で追跡できない（独立した進捗・状態は失われる）。
- ランタイム連結は将来の具体的ニーズ発生時まで保留し、必要になればその時点で再検討する。
