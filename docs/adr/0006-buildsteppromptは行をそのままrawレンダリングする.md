# ADR-0006: buildStepPrompt は行をそのまま（raw）レンダリングする

## Status

accepted

## Context

buildStepPrompt はセクションの中身を `- 箇条書き` としてレンダリングしていたが、単一行のフラットな string[] しか表現できず、段落・番号付きリスト・コードフェンス・サブ見出しを組み合わせたプロンプト（tools Issue #82 の移行対象ワークフローで実際に使われている構成）を箇条書きに押し込むと表現力が損なわれる。

構造化ブロック API（`{ type: "code", ... }` のような宣言的ブロック型）も検討したが、作者が自由に Markdown を書く需要に対して過剰な構造であり、導入しない。

## Decision

buildStepPrompt は各セクションの中身である `string[]` を **1 行ずつそのまま**レンダリングする。

- 各セクションは `## 見出し` + 空行 + 行の連結（`items.join("\n")`）で出力する
- 行へのプレフィックス付与・トリム・空行の自動挿入は行わない
- 空行は作者が `""` アイテムを挟んで明示的に制御する
- 固定 6 セクションの骨格（目的 / 完了条件 / 方針 / 出力 / 注意事項 / インプット）、空セクションの省略、セクション順序は維持する
- シグネチャ（`StepPromptSpec`）は変更しない。純粋フォーマッター（ADR-0002）は維持

## Considered Options

- 構造化ブロック API（discriminated union）: 型安全性は高いが、記述が冗長になり、散文が多いプロンプトでは過剰。不採用。
- 汎用 Markdown ドキュメントビルダー（固定セクション廃止）: 自由だが、見出し規約・順序・空セクション省略の一元管理が失われる。不採用。

## Consequences

- 作者は段落・箇条書き・番号付きリスト・コードフェンス等を自由に組み合わせられる
- 既存ワークフローの手組み `[...].join('\n')` から機械的に移行できる（tools Issue #82）
- 見出しの著作責任は作者に委ねられる（`##` の重複等のアウトライン破壊を防ぐ仕組みはない）
